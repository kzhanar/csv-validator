topic: CSV Validator requirements and validation workflow
updated: 2026-10-06T16:57

- (capability) CAP-1: A user can submit a CSV file containing provider data and receive a validation report; success is a report produced for supported CSV input.
- (capability) CAP-2: The validator checks that provider_id, provider_name, and effective_date columns are present and that each required value is populated; success is an error for missing columns or values.
- (capability) CAP-3: The validator checks that each effective_date value is a valid date; success is an error identifying rows with invalid dates.
- (capability) CAP-4: The validator checks that provider_id values are unique within one uploaded file; success is an error identifying duplicate provider rows.
- (capability) CAP-5: The validation report shows total rows, valid rows, invalid rows, each affected row number, and each error reason; success is a report that makes row-level outcomes inspectable.
- (constraint) Only CSV files are supported, uploaded data must not be stored permanently, and the first version should remain simple.
- (direction) The project is a Java, Spring Boot, Maven, and JUnit learning project; the intended learning path is requirements to specification to stories to test cases to implementation and verification.
- (constraint) Non-goal: persistent storage, non-CSV input formats, and expanded production-scale processing are outside the first version.
- (question) Which date format or parser policy defines a valid effective_date?
- (question) How should row numbers be defined relative to the header, and should one row report multiple validation errors?
- (question) What behavior is required for malformed CSV syntax, unsupported encodings, empty files, and files with extra columns?

- (decision) CSV input is comma-delimited UTF-8 with the first record as headers; required headers are exact and case-sensitive; extra columns are ignored; quoted values containing commas parse as one field, as specified by product-spec.md and US-3.
- (decision) provider_id, provider_name, and effective_date values that are empty or whitespace-only are missing; effective_date must be a real calendar date in strict YYYY-MM-DD format, as specified by product-spec.md and US-4/US-5.
- (decision) provider_id uniqueness compares trimmed values case-sensitively; every row in a duplicate group is invalid, as specified by product-spec.md and US-6.
- (decision) Data rows are numbered from 1 after the header; a row with multiple errors is reported once with every reason; invalid rows count once and total rows equal valid plus invalid, as specified by product-spec.md and US-7.
- (decision) Missing required headers are reported as file-level errors, all missing headers are identified, and row validation does not run; additional columns do not fail validation, as specified by US-3 and story-3-test-cases.md.
- (decision) The browser accepts one non-empty CSV upload; missing-file and unsupported-file submissions receive clear errors; file-type rejection is server-side and does not rely only on browser-provided content type, as specified by US-1/US-2.
- (constraint) Uploaded contents and reports are request-scoped and are not permanently stored; no upload/report history is provided, and CSV row values are not logged, as specified by product-spec.md and US-9.
- (question) What maximum upload size should be accepted?
- (question) How should malformed CSV syntax, zero-byte files, blank data records, and non-UTF-8 input be reported?
- (question) Should unsupported file types be determined by filename, parsed content, or both? Server-side rejection must not rely only on browser-provided content type.
- (decision) CSV is comma-delimited UTF-8 with a header record; required headers are exact and case-sensitive, extras are ignored, and quoted commas parse correctly. Empty or whitespace-only required values are missing. effective_date is a real date in strict YYYY-MM-DD format (product-spec.md, US-3/4/5).
- (decision) provider_id comparison trims surrounding whitespace, preserves case, and marks every row in a duplicate group. Data rows number from 1 after the header; rows with multiple errors are listed once with every reason; total equals valid plus invalid (product-spec.md, US-6/7).
- (decision) The browser flow accepts one non-empty CSV; missing or unsupported uploads get clear errors and file-type rejection is server-side, not based only on browser content type. Uploaded contents/reports are request-scoped, with no permanent storage, history, or CSV-value logging (US-1/2/9).
